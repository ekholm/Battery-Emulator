# Published module artifacts

Machine-readable artifacts a Battery-Emulator device resolves against at run time.
Nothing here is source; every file is generated by `tools/gen_publish_manifests.py`
from a finished build, and this branch is replaced rather than edited by hand.

    manifests/meta.json                 which manifest answers for which core / string table
    manifests/manifest-<core_id>.json   the module blobs built for that exact core
    manifests/i18n-manifest-<id>.json   the language packs binding that TR key table
    blobs/*.bemod                       driver modules, matched to one core
    i18n/*.blp                          language packs

## Why a branch rather than release assets

The device serves its own web page from a LAN address, so the browser fetch is
cross-origin. Release-asset downloads were measured to carry no
`Access-Control-Allow-Origin` on any route - the `releases/download` redirect, the
signed storage URL, and the API route with `Accept: octet-stream` all fail, the last
because the browser re-checks CORS on the final response. `raw.githubusercontent.com`
serves `ACAO: *`, so the files a browser reads live on a branch and are fetched raw.

## Matched sets

A `.bemod` blob is linked against one core build and carries that `core_build_id`.
The manifest is discovery only: the id is validated at upload and again when the
module is mapped, so a stale manifest can fail to offer a module but cannot install
a mismatched one. `sha256` is transport integrity for the browser.
